# Последовательность реализации и выпуска

Этапы ниже относятся к будущей разработке. Фактически подготовлены материалы передачи; ни один runtime gate пока не пройден. Команда для планирования: 2 инженера полного цикла, 1 QA, частичное участие дизайнера/DevOps/юриста; это исходное допущение, не утверждение о доступных сотрудниках. Человеко-дни в backlog не делятся механически на число людей: финансовая модель, доступы каналов и миграция лежат на критическом пути.

## P1. Основание и повседневная работа

**Порядок.** TASK-OPS-005 окружения/CI → IAM регистрация/сессии → ORG tenant → приглашения и scope → объекты/единицы → базовые тарифы и гости → создание брони и ограничения PostgreSQL → календарь → ручные платежи/ledger → первоначальные отчёты и уведомления. Точный DAG задан depends_on в backlog.json. Переключение организаций, журналирование и защита ПД встраиваются до загрузки каких-либо реальных данных.

**Результат.** Менеджер ведёт синтетическую организацию: объект, цена, гость, бронь, перенос, отмена, ручное поступление, долг, расходы, календарь и отчёт. Два клиента полностью изолированы. Реального канала и карты оплаты ещё нет.

**Gate G1.** Все P1 проверки выполнены; 100 конкурентных попыток занять одну единицу дают ровно одно активное размещение; скрытый tenant не читается через REST/search/export/cache/jobs; posted ledger сбалансирован; основные действия выполняются клавиатурой; ошибок P1/P2 без решения нет. Основа ПД проверена до следующего этапа.

## P2. Полные операционные сценарии

**Порядок.** Расширенные цены/длительность/дети/промокоды и preview → номерной фонд с нераспределёнными бронями → витрина и приватная страница гостя → документы/условия с юридической проверкой → дополнительные услуги, партнёры → уборки/поломки/закупки/счётчики/начисления → аналитика и шаблоны сообщений → import mapping/dry-run → ограничения тарифа.

**Результат.** Закрыт набор документированных пользовательских процессов, который не требует внешнего API-доступа. Оплата в модуле может использовать подтверждённый ручной процесс до провайдера; интерфейс не показывает неработающее онлайн-списание как доступное.

**Gate G2.** У каждого обязательного требования есть доступный экран/существенные состояния, задача, тест и доказательство. Все totals golden dataset сходятся. Миграционный dry-run не имеет неучтённых строк и не выполняет внешние действия. Статусы/ID/финансовые источники первого клиента, отсутствующие в исходном Excel, заведены как конкретные незакрытые требования к данным.

## P3. Подключения, платежи и устойчивый обмен

Запросы договоров/доступов начинаются параллельно P1, без подключения к рабочим аккаунтам и без отправки от имени владельца до разрешённого действия. Техническая реализация начинается после G2 для критичных операций брони/денег.

1. Зафиксировать capability matrix и способы авторизации для каждого паспорта. Свой partner API-Key KeyCalendar не заменяется ключом интеграции RealtyCalendar. Письменно подтвердить квоты/сертификацию/стоимость.
2. Реализовать общий inbox/outbox, idempotency, leases, reconciliation, conflict queue и safe retry. Это TASK-INT-001..004; адаптеры используют их, не дублируют.
3. Приоритетные booking adapters: **Авито и Суточно.ру**. Если API закрыт, задача остаётся заблокирована на доступе; iCal при подтверждённой поддержке описывается как отдельный ограниченный канал и не закрывает API-паритет.
4. Платежи: сначала подтверждённый merchant contract с провайдером, покрывающим нужныe first-client сценарии проживания/залога/возврата/чека; паспорта Монета физ./юр. рассматриваются отдельно. YooKassa и другие обнаруженные кандидаты не объявляются подключёнными по рекламному упоминанию. Текущая форма бизнеса и merchant ещё требуют определения.
5. Подключить остальные текущие каналы, CRM, замки, pricing и сообщения по отдельным TASK-ADP. Общий iCal parser переиспользуется, но UID/cancel/timezone/доступ конкретного сервиса проверяются отдельно. Исторические названия получают сначала discovery, а не фиктивный live adapter.
6. Выполнить sandbox → разрешённый test property → сверка → ограниченное production подключение. Не отправлять тестовую бронь гостю и не отменять реальную ради проверки. Если sandbox нет, описать согласованную с провайдером безопасную процедуру и владельца ручной проверки.

**Gate G3 по каждому подключению.** Документирован доступ; mapped objects/rates без неоднозначностей; каждое объявленное направление и каждая операция прошли тест; webhook reorder/replay и timeout не дублируют эффект; после outage выполняется сверка; видны stale/error/reconnect/conflict; rollback/disconnect не теряет подтверждённые события. Применимый full parity gate не закрывается при обязательном недоступном подключении.

## P4. Перенос, пилот и следующие клиенты

**Подготовка среды.** Отдельное production окружение в РФ, TLS-домен, секреты, ресурсные лимиты, финансовая/правовая модель, резервное копирование и ответственный дежурный. Текущая ВМ с соседним SkySend не модифицируется из материалов планирования. Развёртывание будущего SaaS требует отдельной задачи и учёта существующих служб; нельзя переиспользовать их DB/users/ports без согласованного дизайна.

**Данные.** Следовать [migration-spec](../data/migration-spec.md). Экспорт первого клиента есть, но без стабильных ID, статусов, валюты и платежного журнала. Получить дополнительные официальные источники/подписанные ручные решения → сверить 100% будущих обязательств → dry-run → повтор dry-run → rehearsal rollback → согласовать окно → финальный snapshot/delta → один writer → read-only verify → включение каналов по одному. В текущей работе apply не запускается.

**Пилот.** Один tenant, согласованные сотрудники и объекты. Первые 72 часа усиленное наблюдение, далее минимум 14 календарных дней с ежедневной сверкой. Успех: нет потери броней/платежей, все конфликты имеют решение, SLO достигнут, restore проведён, owner подтверждает ключевые сценарии. Критичный сбой останавливает новые подключения и расширение; новые внешние факты продолжают долговечно приниматься.

**Следующие клиенты.** После G4 подключить малую группу 3–5 организаций (проектный размер), разные портфели/права/каналы; повторить onboarding/tenant negative tests и support runbook. Лимиты/стоимость/договор опубликованы только после утверждения. По результатам расширять лимиты с измерением, не менять их задним числом.

## Ворота и ответственные

| Gate | Условие | Ответственный будущей реализации | Связанные документы |
|---|---|---|---|
| G0 Requirements ready | Реестр/источники/экраны/задачи/тесты связаны; неизвестное отмечено | Product + tech lead | requirements, design/screens, backlog |
| G1 Core safe | Isolation, race, ledger, базовая доступность UI пройдены | Tech lead + QA | [testing](testing.md) |
| G2 Operations ready | Все независимые от закрытых API процессы готовы, частичные данные не маскируются | Product + QA | [реестр функций](../requirements/reference.json) |
| G3 Provider ready | Договор/доступ/capability/sandbox/reconcile для каждого активируемого сервиса | Integration owner | [каталог](../integrations/catalog.json) |
| G4 First customer safe | Полная сверка активных данных, restore и rollback, юридические gates, pilot sign-off | Owner клиента + migration lead | [перенос](../data/migration-spec.md), [compliance](../research/legal/compliance.md) |
| G5 General launch | Малый multi-tenant cohort, мониторинг, поддержка, тарифы, итоговый parity report | Product owner + operations | backlog, incidents, legal gates |

Противоречие «этап P1» в исходной feature записи и более поздняя зависимость отражается `phase_dependency_note` в backlog: выполнять по его DAG, не обходить зависимость ради номера этапа. После декомпозиции команда может разделить задачу на foundation и finishing, сохранив исходный requirement ID.

## Дополнения после обязательного объёма

SSO, произвольные формулы расчётов с собственниками, клиентский публичный API и дополнительные платёжные провайдеры старого прототипа не являются автоматически подтверждённым паритетом. Для них сначала отдельное требование со статусом proposed, актуальное исследование доступа, экран, оценка и тест. Никакой такой пункт не должен задерживать критичные исправления календаря/денег или вытеснять подтверждённый Autopilot.
