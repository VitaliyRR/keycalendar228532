# Кей Календарь — веб-клиент

React 19, TypeScript, Vite. Исходники приложения в `src/`; Golos Text с лицензией в корневом `assets/fonts/OFL.txt`. Цвета, размеры и плотность взяты из `design/tokens.json` и макетов.

## Запуск

Из корня репозитория после `npm install`:

```powershell
npm run dev:web
```

По умолчанию интерфейс: `http://127.0.0.1:5173`, proxy `/api` → `http://127.0.0.1:3001`. При другом адресе API задать `VITE_API_TARGET` для dev proxy или `VITE_API_BASE` для размещённого клиента. Браузерные запросы используют cookie, CSRF из `/auth/me`, `Idempotency-Key` для команд и `If-Match` для изменения версий.

```powershell
npm run typecheck -w @keycalendar/web
npm run build -w @keycalendar/web
```

## Рабочие маршруты

- `/login`, `/register`, `/verify-email`, `/recovery`, `/reset-password`, `/setup` — доступ и рабочее пространство.
- `/o/:orgId/SCR-CAL-01` — шахматка с фильтрами, клавиатурным выбором дат и мобильным списком.
- `/o/:orgId/SCR-RES-01…04` — реестр, создание, карточка, расчёт изменения и отмены.
- `/o/:orgId/SCR-OBJ-01…02` — объекты и номера; `SCR-CAL-03` — блокировка дат.
- `SCR-RTE-01/04`, `SCR-FIN-01/02`, `SCR-REP-01/02`, `SCR-OPS-02/03`, `SCR-INT-01/02`, `SCR-MIG-01/02` — соответствующие операции с API.
- Остальные SCR-ID открывают данные указанного ресурса с серверными состояниями загрузки, пустого результата и отказа. Они не означают завершение всего функционального требования соответствующего экрана.

Экраны используют только ответы сервера. Сервер подтверждает доступность, цену, права, финансовый результат и состояние доставки. Ошибки 403, 409, 412 и отсутствие сети показываются явно. Секреты и клиентские экспорты не входят в bundle.

## Границы текущей реализации

Подключение внешних площадок, фактическая доставка сообщений, приём платежей через провайдера и применение клиентской миграции требуют серверных возможностей и подтверждённых внешних допусков. Интерфейс не показывает отсутствующую интеграцию как рабочую. Широкий каталог из 77 SCR-ID содержит частично реализованные маршруты; степень завершения каждого требования нужно подтверждать runtime-тестом на связанном API, а не наличием страницы.
