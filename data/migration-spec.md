# Перенос первого заказчика: спецификация и критерии допуска

Статус 24.09.2026: в закрытом staging выделенной базы Кей Календаря сохранены 19 зашифрованных пакетов исходных свидетельств RealtyCalendar, всего 45 802 физические строки. Повторная загрузка дала ноль новых строк. Это этап 0: действующие объекты, гости, брони, платежи и подключения каналов не созданы. Исходный RealtyCalendar не изменён. Приватная матрица содержит объём, хэши и физические индексы строк; репозиторий их не раскрывает. Процедура загрузки описана в [runbook](import-stage0-runbook.md).

Связь: REQ-MIG-001..004, SCR-MIG-01..03, TASK-MIG-001..004, TEST-MIG-001..004. Все созданные ниже правила трансформации являются проектом KeyCalendar.

## Что доказано источником

В штатном экспорте ровно девять колонок: «Объект», «Заезд», «Выезд», «Контакты», «Примечания», «Гостей», «Сумма», «Источник», «Менеджер». Нет стабильного ID бронирования/объекта, статуса брони, валюты, платёжных транзакций/возвратов, внешнего ID канала, полной истории изменений и условий тарифа. Выгрузку нельзя напрямую интерпретировать как полный набор активных подтверждённых броней.

Дополнительно сохранены отдельные снимки таблиц клиентов, расходов, оплат, залогов, каталога 34 лотов, настроек, полных карточек всех 34 объектов и всех 56 будущих броней. Общая пагинация списка остановилась на странице 61 (1 525 ID), поэтому в режиме чтения сохранены помесячные страницы за 51 месяц, январь 2023 — март 2027. Они содержат 5 641 уникальный стабильный ID брони RealtyCalendar, включая все прежние 1 525; штатный Excel содержит 5 640 строк без ID. Предварительная сверка даёт 5 624 точных совпадения по полям, 13 строк в пяти группах с одинаковыми сигнатурами и четыре расхождения будущих броней: два отличия контакта, одно изменение даты выезда и суммы, одна UI-бронь без строки Excel. Всего в UI 56 будущих броней против 55 в Excel. Владелец подтвердил использование текущих карточек RealtyCalendar для этих четырёх расхождений; их исходные ID и решение сохранены только в закрытом наборе. Это решение не заменяет финальную дельту перед переносом и проверку остальных идентичностей. Совпадение по одинаковой сигнатуре не доказывает тождество записей без проверки источника.

Из 34 названий Excel 28 буквально совпадают с каталогом; для шести подготовлены приватные строки проверки владельцем. В 20 032 видимых строках оплат встречаются 9 367 разных ID броней; вместе с 5 641 ID месячных страниц это 9 520 уникальных ID: 3 879 только в оплатах и 153 только в месячном списке. У 171 строки оплат нет ссылки на карточку брони, поэтому она не входит в подсчёт ID по ссылкам. Это расширяет область сверки, но не делает строки оплат готовыми платёжными проводками или доказательством статуса брони. В карточках всех 34 объектов видны границы окна заезда 14:00–22:00 и выезда 09:00–12:00, но нет IANA timezone. Владелец сообщил, что часовые пояса объектов различаются; требуется подтверждение зоны каждого лота, нельзя назначать её по городу или адресу. Доступны 578 проверенных миниатюр JPEG 100×100, исходные изображения полного размера в наблюдаемом интерфейсе не найдены. До сверки расхождений, зон, статусов и смысла денег действующие обязательства и денежный журнал не создаются.

Для 3 879 ID, видимых только через оплаты, текстовые названия разделились на 3 337 ID с 25 метками, отсутствующими в нынешнем каталоге 34 лотов, и 542 ID с привычными метками. Полные карточки и история по одному представителю каждой из 25 отсутствующих меток подтвердили 25 разных исходных ID исторических лотов; все они вне нынешнего каталога. Ещё 16 полных карточек и историй с привычными метками показали статус отмены. Эти 41 карточка сохранены в двух зашифрованных пакетах `booking_card_facts_ui` как выборка; они не классифицируют все 3 879 броней. Для полноценной истории нужны дальнейший просмотр карточек, утверждённая схема исторических лотов и соответствие каждой записи целевому исходу; не привязывать их автоматически к активным 34 объектам.

Контакты и примечания содержат свободный текст; депозит, продление, количество гостей или частичная оплата могут быть упомянуты текстом. Такие упоминания создают задачу ручного подтверждения, а не финансовую проводку или автоматическое изменение проживания. Поле «Сумма» не считается оплатой. Публичные макеты используют искусственные значения.

## Ключи, дубли и связи

`source_locator = export_checksum + worksheet_name + physical_row_number` уникален только в этом снимке. Это позволяет повторить dry-run того же файла без дублирования. Для разных выгрузок сравниваются кандидаты (объект/даты/контакт/сумма) с уровнем уверенности; автоматическое слияние без стабильного source ID запрещено. Совпадение всех колонок также может означать две разные записи. Таблица решений хранит reviewed_by, reviewed_at, evidence_ref, old/new candidate, reason.

Target UUID генерируется независимо от ПД. Таблица source-target map зашифрована в закрытой staging БД. Собственный номер брони не строится из телефона или адреса. Изменённая строка сохраняет связь с предыдущим review, но требует повторной проверки. Похожие имена объектов нельзя объединять без подтверждения каталога.

## Manifest закрытого набора

`package_id, collected_at, source_system, source_export_method, filter_scope_description, file_name, media_type, sha256, byte_size, worksheet_names, row_count_by_sheet, known_columns, missing_fields, local_encrypted_location, access_principals, retention_due_at, parser_version, normalization_hash, review_state`.

Checksum вычисляется до чтения парсером и после передачи. Оригинал immutable. XML parser не разрешает DTD/external entities, макросы и сетевые ссылки; размер/число строк/глубина XML ограничены. Formula cells сохраняются как evidence и не исполняются. Приватный manifest не копируется в issue, PR, макет или screenshot. Файлы в РФ при облачном хранении; сроки retention утверждает оператор.

## Последовательность будущей миграции

1. **MIG-0 Inventory.** Зафиксировать границы tenant, перечень объектов/единиц, часовые пояса, пользователей, будущих и исторических броней, каналов, тарифов и денежных отчётов. Определить отсутствующие поля и источники их закрытия. Текущий экспорт даёт часть этого шага.
2. **MIG-1 Normalize.** Разобрать readonly-копию в закрытый staging; не открывать внешние ссылки, не отправлять письма. Создать ImportRecord и review_flags; отчёт totals только приватно.
3. **MIG-2 Review mapping.** Owner утверждает соответствие действующих и исторических объектов, статусы броней, смысл сумм, валюту, тарифы, source IDs и финансовую стратегию. Для четырёх известных будущих расхождений приоритет текущих карточек RealtyCalendar подтверждён; все будущие брони всё равно повторно сверяются по финальной дельте. Допустим отдельно подтверждённый начальный остаток по каждой брони с датой среза вместо выдуманной исторической разбивки; отметить completeness=opening_balance_only.
4. **MIG-3 Dry-run.** Пустая изолированная staging БД, egress deny, уведомления/платежи/каналы off. Загрузить справочники → guests → reservations/stays → allocations → согласованные finance evidence/opening balances → channel mappings. Транзакции пакетами с ImportBatch и rollback mark; выполнить все инварианты.
5. **MIG-4 Reconcile.** Сверка 100% будущих броней и денег, count по объекту/месяцу/источнику, orphan=0, unexplained duplicates=0, overlap без разрешённого incident=0, суммы по валютам и semantics. Ручная выборка прошлой истории минимум 30 строк либо весь набор, если меньше; рискованные записи 100%. Значения из первого клиента остаются приватными.
6. **MIG-5 Rehearsal.** Повтор того же snapshot даёт нулевые новые сущности и тот же manifest. Новый snapshot требует delta matching review. Измерить duration и rollback, подписать отчёт владельцем.
7. **MIG-6 Cutover.** Только после отдельного согласованного окна: остановить ручные изменения в старом процессе по инструкции владельца; финальная выгрузка/delta и сверка; old outbound каналов выключает уполномоченный пользователь официальным способом; убедиться в отсутствии двух writers; загрузить target и readonly-проверку; новые API включать по одному каналу.
8. **MIG-7 Pilot.** Первые 72 часа усиленная сверка каждые разрешённые окна API, ежедневная полная сверка денег/занятости; затем 14 дней наблюдения. Хранить старый источник доступным readonly на согласованный срок.

Загрузка исходных свидетельств на рабочей ВМ выполнена по запросу владельца. Нормализация в действующие таблицы, изменение источника и переключение каналов остаются отдельными шагами после сверки; этот документ сам по себе не запускает их автоматически.

## Сверка и критерии остановки

Каждый показатель: source_value, target_value, difference, allowed_reason, evidence_ref, reviewer, status. Count строки не заменяет count реальных броней при отсутствии ID. Coverage будущих броней считается после review идентичности. Проверяются min/max даты, stay nights, status/source distributions, суммы без смешения валют, связь каждой строки с target/disposition. Quarantine сохраняется и показывается владельцу; скрывать отбракованные строки нельзя.

Стоп: неясный будущий статус, несопоставленный объект, денежное расхождение, потерянный external ID нужного канала, unresolved overlap, неизвестное назначение залога, нарушение isolation, непроверенный restore. Допуск возможен только после разрешения или документированного исключения конкретной исторической записи без влияния на активные обязательства. Нельзя подписать полную миграцию с неизвестными активными бронями.

## Откат

До cutover: удалить данные только batch из изолированной staging по source-target map, восстановить snapshot и проверить независимые записи. После cutover rollback не является простым восстановлением вчерашней БД: новые брони/деньги существуют у каналов и гостей. Сначала stop new writes/hold new sales, сохранить delta всех событий с cutover, сверить внешние факты, перенести подтверждённые новые обязательства в выбранную рабочую систему и только затем вернуть writer. Никогда не стирать успешный платёж и не повторять списание для «восстановления».

Ответственные будущего перехода: owner клиента утверждает данные/окно; migration engineer выполняет; QA проверяет; integration owner подтверждает один writer; on-call владеет rollback. Конкретные имена и приватные контакты в закрытом runbook.
