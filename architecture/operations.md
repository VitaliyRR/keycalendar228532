# Эксплуатация, восстановление и поддержка

Связь: REQ-OPS-001..006. Эти параметры проектные; реальной промышленной инфраструктуры и SLA ещё нет.

## Окружения

| Окружение | Данные | Внешний обмен | Назначение |
|---|---|---|---|
| local | Только synthetic | Mock contracts, egress выключен | Разработка модулей |
| CI | Только synthetic, временная БД | Контрактные fixtures | Блокирующие проверки |
| staging | Synthetic; отдельная закрытая migration staging при необходимости | Sandbox с отдельными ключами; реальные каналы запрещены | E2E, нагрузка, rehearsal |
| pilot | Один согласованный tenant | Только каналы с допуском, постепенное включение | Первая промышленная эксплуатация |
| production | Реальные tenant | Production secrets, персональные квоты | Следующие клиенты |

Разные базы, bucket, ключи, email sender и merchant accounts. Заголовок окружения в административном UI. Staging не получает копию production целиком. Секреты выдаются workload identity/закрытым secret store. Deploy-пользователь не root, runtime без права DDL. Требуются TLS-домен, firewall, запрет прямого доступа к DB и согласованный перечень исходящих адресов интеграций.

## Обновление

Релиз содержит immutable image digest, SBOM, скан зависимостей, соответствующую версию schema и manifest. Миграции expand → dual-compatible app → backfill → verify → contract отдельным релизом. До применения оценить lock duration на production-like объёме. Безопасный откат приложения возможен к прошлой совместимой схеме; разрушительная обратная SQL-миграция не заменяет восстановление. Один tenant feature flag включает изменение пилотно. Отключение флага прекращает новые команды, не уничтожает данные.

## Резервные копии

База: ежедневный base backup + непрерывный WAL в отдельное хранилище РФ; проектное удержание PITR 14 дней, 30 ежедневных и 12 месячных копий после согласования сроков. Файлы: versioning, manifest/checksum, lifecycle, отдельные ключи. Secrets backup отдельно, доступ минимум двух назначенных операторов. Правовые сроки могут потребовать иного хранения; см. материалы compliance.

Restore-runbook: объявить инцидент → зафиксировать cut-off → запретить исходящие интеграции → восстановить в новом изолированном окружении → применить WAL до точки → проверить schema, RLS, tenant counts, FK, ledger balance, активные allocation, files checksums → собрать события, принятые после точки из durable inbox/провайдера → сверить внешние подтверждения/оплаты → заменить endpoint → постепенно включить workers. Результат измеряется actual RPO/RTO. Восстановление одного tenant выполняется из отдельной восстановленной копии, с фильтрованным импортом и сверкой; нельзя откатывать всех клиентов из-за одного.

Ежемесячное упражнение должно включать потерю primary, испорченный последний архив и отсутствие части WAL. Успех: потеря ≤ 15 минут, возврат API ≤ 4 часа, 0 пересечений новых allocation, 0 несбалансированных posted journal, 0 утечек tenant. Если цель не выполнена, записывается измеренный результат и блокируется обещание SLA.

## Метрики и тревоги

| Сигнал | Начальный порог | Реакция |
|---|---|---|
| HTTP 5xx / latency | > 2% за 5 мин / p95 > 2 сек за 10 мин | OPS on-call, rollback/capacity по runbook |
| Outbox oldest age | > 5 мин, критично > 15 мин | Проверить зависший lease/канал; banner пользователю |
| Channel auth / quota | Первый 401/403; длительный 429 | reconnect_required / throttle, без слепых retries |
| Availability drift | Подтверждённый mismatch занятого диапазона | Incident высокого приоритета, возможный stop-sell по официальной операции |
| Payment unknown | > 15 мин | Reconcile провайдера, ручная очередь без дубля списания |
| Backup freshness | WAL > 15 мин или base > 26 ч | Incident; проверить хранилище/ключи |
| DB saturation | disk > 80%, connections > 80%, replication lag > 60 сек | Capacity/slow query; stop heavy exports |
| Isolation violation | Любая | P1 security incident, закрыть уязвимый маршрут |

Метрики метят channel_code и environment; tenant_id допустим в ограниченном trace, но не бесконечными labels в общем Prometheus. Секреты/полные ПД в error tracker не отправлять. Панель поддержки показывает маскированные идентификаторы, время ошибок, версии, очереди и статус восстановления.

## Реагирование

P1: утечка, массовая недоступность, двойные продажи, некорректное списание; P2: сбой одного канала/отчёта без потери данных; P3: косметика. Дежурный назначается до пилота, контакты хранятся в закрытом runbook. Инцидент имеет time line, owner, mitigation, проверку восстановления и корректирующую задачу. Пользователю показывается фактическое состояние: «Бронь сохранена. Канал ещё не подтвердил обновление».

Поддержка не может менять платежи через SQL. Разрешённые административные команды имеют те же доменные проверки, audit, reason и временное полномочие. Security incident запускает отдельный юридический процесс уведомлений с проверенными сроками из compliance; персональные сведения не публикуются в общем status page.
