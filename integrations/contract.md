# Договорённости для всех интеграций

Дата проверки источников: 24.09.2026. Это спецификация для реализации, рабочие соединения не создавались.

## Статусы доказательств

`DOC` означает подтверждение в официальной документации указанного сервиса или RealtyCalendar (RC). `HISTORICAL` означает только историческое упоминание в официальных материалах. `ACCOUNT-SOURCE` означает название в фильтре источников исследованного аккаунта, без подтверждения подключения. `PROPOSED` означает решение для Кей Календаря. Наличие коннектора RC не даёт Кей Календарю права использовать его ключи, партнёрский договор, webhook-адреса или API.

В каждом паспорте отдельно указаны доступ, направления и ограничения. Состояние `external_access_pending` означает незавершённую внешнюю зависимость. Оно не превращается в «подключено» после сохранения настроек. `not_applicable` относится к сущности, которая не относится к назначению интеграции; `unknown` не равно `unsupported`.

## INT-CORE-001. Подключение и возможности

Проектное решение: состояния `not_configured → access_pending → credentials_valid → mapping_incomplete → verification_pending → healthy/degraded/reauth_required/paused`. Права: владелец или администратор с `integration.manage`; оператор видит доступность каналов по разрешённым объектам; финансовые ключи доступны только отдельной роли. Отображать возможности отдельно для каждого соединения, объекта, тарифа и версии договора. Запрещено выдавать iCal за API или принимать неподдерживаемое ограничение молча.

До активации: подтвердить договор/допуск, версию протокола, scopes, объект и тариф, согласовать источник истины, прочитать текущее состояние площадки, показать план первых изменений, выполнить согласованные тесты, сохранить протокол проверки. Отдельное согласие на реальные контрольные бронирования и платежи необходимо на этапе подключения; исследование этого этапа не выполняет.

## INT-CORE-002. Сопоставление

Ключ соединения: `tenant_id + provider + provider_account_id`. Карта: `connection_id + external_property_id + external_room_type_id + external_rate_id → property_id/unit_type_id/rate_plan_id`; nullable поля разрешены только по capabilities. Внешний ID объявления, ID гостиницы, ID категории, код синхронизации и ключ API имеют разные поля и типы. Нельзя сопоставлять по адресу или имени автоматически. Предлагать кандидатов, подтверждать человеком, проверять количество мест, квоту, валюту и часовой пояс. Уникальность external binding внутри соединения; одинаковый внешний ID другого tenant не должен раскрывать данные.

## INT-CORE-003. Направления и источник истины

| Поле | Предлагаемый владелец | Правило конфликта |
|---|---|---|
| Идентификатор OTA-брони, её подтверждение/отмена, цена уже заключённой OTA-брони, OTA-комиссия | Исходная площадка | Сохранять поступивший факт; локальную корректировку хранить отдельно с причиной. Отмена в локальном календаре не означает отмену на площадке |
| Прямая бронь и блокировка | Кей Календарь | Транзакционная защита от пересечения; права и аудит |
| Будущие квоты/цены/поддержанные ограничения | Кей Календарь после завершённого переключения | Один отправитель на канал; версии desired/last_sent/acknowledged/observed раздельны |
| Факт оплаты, возврата и выплаты | Платёжный провайдер, сверенный с реестром | Не изменять после редиректа гостя или лишь webhook без проверки подлинности |
| Ручная оплата | Кей Календарь | Отдельный ledger entry, не подмена online-транзакции |
| Контакты гостя | Источник поля + локальная версия | Скрытые контакты не стирают известные; хранить минимально нужный состав |
| Договор/подпись | Поставщик ЭДО | Идентификатор, версия документа, статус и доказательство; не выводить «подписан» из отправленной ссылки |
| Замок и фактический код | Поставщик доступа | Сохранённый код не доказывает работоспособность; отображать последнюю проверку |

## INT-CORE-004. Двойные бронирования

Интервал проживания `[check_in, check_out)` в локальных датах объекта. UTC использовать для времени событий; DST и переход через полночь покрыть тестами. Для отдельной единицы размещения транзакционно запрещать пересекающиеся активные occupancy; для категорий атомарно резервировать квоту по ночам. Две независимые площадки могут продать последнюю квоту до получения обновления: абсолютную гарантию отсутствия овербукинга обещать нельзя.

При входящей конфликтной подтверждённой брони: сохранить inbox и внешний факт, открыть `booking_conflict`, поставить затронутый инвентарь на закрытие каналам, уведомить ответственного, запретить автоматическое уничтожение/перезапись одной из броней. Сотрудник сверяет статус на площадке, выбирает переселение/согласованную отмену, фиксирует источник решения. Временный hold имеет TTL; TTL прямой неоплаченной заявки не применяется автоматически к подтверждённой OTA-брони. При отмене после заезда нужна отдельная проверка фактического проживания и денег.

## INT-CORE-005. Дубли, порядок событий, доставка

Все следующие параметры проектные, не SLA поставщиков. Inbox хранит `tenant_id, connection_id, external_event_id/version, received_at, payload_hash, schema_version, processing_state`. Бронь идентифицируется по соединению и `external_booking_id`, не по ФИО/датам. Повторное событие подтверждать после durable-write; при отсутствии event ID использовать семантический fingerprint, затем fetch актуального объекта. События разных версий упорядочивать по provider sequence/version, время получения само по себе недостаточно. При неизвестном порядке запросить snapshot и пометить конфликт, не делать last-write-wins вслепую.

Outbox записывается в одной транзакции с изменением доступности. Ключ отправки: connection/entity/date-range/desired-version/operation. После timeout проверять состояние/идемпотентный результат, прежде чем повторять. Никогда не повторять вслепую charge/refund/выдачу кода. Уважать `Retry-After`, квоты, подписи и контракт провайдера. Предлагаемый backoff при 5xx: 5с, 30с, 2м, 10м, 30м с jitter; числа окончательно настраиваются по договору. 401/403 → остановка отправки и переавторизация; 400/422 → корректировка данных; 409 → сверка версии; 429 → планирование по лимиту. Poison events в DLQ, повтор только с сохранённым исходным ID и аудитом.

## INT-CORE-006. Журнал, секреты и восстановление

Журнал по операции: correlation ID, связь с бронью, направление, masked resource ID, версия, время постановки/отправки/ACK, HTTP/бизнес-код, число попыток, оператор, diff разрешённых полей. Пароли, access/refresh tokens, iCal URL с секретом, коды замков, PAN/CVV, паспорта и полный webhook payload не выводить в логи. Диагностику хранить с ограничением доступа/срока; изолировать tenants. Секреты шифровать отдельным KMS/secret store, ограничивать scopes, поддержать ротацию и отзыв.

После сбоя: восстановить checkpoint → получить актуальные брони/отмены с перекрытием окна → идемпотентно применить → пересчитать доступность → сравнить desired/observed → восстановить отправку → сверить деньги отдельно. Удаление локального подключения не закрывает продажи на стороне OTA. Процедура отключения обязана явно показать дальнейшую судьбу продаж и webhook/ключей.

## INT-CORE-007. iCal

iCal переносит интервалы занятости, иногда ограниченный SUMMARY, а не полноценные брони/платежи/цены. URL является секретом. Ключ `connection_id + calendar_id + UID + RECURRENCE-ID`; хранить SEQUENCE/DTSTAMP при наличии. Импорт проверяет HTTPS, размер/таймаут, private/loopback IP и DNS rebinding (SSRF), формат, эксклюзивный DTEND, timezone, повторения, отменённые события. Отсутствие события в одном неполном/ошибочном ответе не открывает даты. Для удаления нужна успешная полная выборка и проверяемая политика исчезновения; циклический реэкспорт исходного события запрещён. Не добавлять контакты гостей в публичный feed. Плановый опрос определяется условиями площадки, последняя успешная синхронизация и возраст данных видны пользователю. Публикация feed не подтверждает его прочтение другим сервисом.

## INT-CORE-008. Проверки и готовность

Общий обязательный набор для каждого API-канала: новая/изменённая/отменённая бронь, повтор, обратный порядок, потерянный webhook, timeout после успешной обработки, 401/429/5xx, недоступный объект, неверный mapping, смена тарифа, валюты и TZ, закрытие последней квоты, поздняя отмена, повторный импорт, отключение и восстановление. iCal: частичный feed, пустой ответ, UID collision, disappearing event, UTC/date-only, loop, запрещённый URL. Платежи: поддельное уведомление, повтор, частичный возврат, возврат после выплаты, чек и деньги с разными статусами. Замки: offline, частичный успех нескольких замков, отмена и продление, отозванный доступ. CRM/сообщения: повторная отправка, opt-out, отозванный token, устаревший event.

Условия `production_ready`: подписанное право подключения; актуальная schema/capability matrix; ключи конкретного клиента; отдельный sandbox либо письменный безопасный план production-тестов; все применимые кейсы пройдены; замер p50/p95/p99 и максимального отставания на пилоте; runbook и ответственный; tenant-isolation test. Отсутствие sandbox не разрешает экспериментировать в реальном аккаунте.

## INT-CORE-009. Переключение первого клиента

Сначала сверить импорт и занятость всех каналов; зафиксировать момент среза и новые события; согласовать контролируемое окно продаж. Отключать старого менеджера по одному каналу только после плана отката. Запретить одновременную запись RC и Кей Календаря. Подключить новый одобренный provider, подтвердить mapping и выгрузку закрытых дат, сверить реестр броней, затем открыть продажи. При откате остановить новые записи, выгрузить дельту, сверить занятость и вернуть прежний manager по процедуре поставщика. Не открывать все даты для «лечения» синхронизации без сверки. Этот этап отложен до реализации и допуска.

Источники общих наблюдений RC: [API и особенности отмен](https://confluence.lan.realtycalendar.ru/kb/osobennosti-raboty-sinhronizatsii-s-kanalami-30958475.html), [работа с внешней бронью](https://confluence.lan.realtycalendar.ru/kb/sozdanie-sobytiya-zayavka-bron-otmena-ili-udaleno-30957142.html). Остальные правила выше являются требованиями Кей Календаря.
