# INT-FIRSTOFD. Первый ОФД

Проверка: 24.09.2026. Статус: `DOC`, кассовый субпровайдер / ОФД в цепочке Монеты; не подтверждение прямого API-коннектора RC. Кей Календарь: `external_access_pending`.

Источник: [Монета для ИП/юридических лиц, список касс](https://confluence.lan.realtycalendar.ru/kb/podklyuchenie-monety-dlya-yurlits-i-ip-48432578.html).

## Подтверждение и подключение

RC предупреждает об отсутствии ссылки на чек в RC.

Назначение: фискальная обработка/доставка сведений о расчётах через согласованную цепочку касса → ОФД. Механизм в найденной инструкции: настройки Монеты/PayAnyWay и кассового сервиса. Прямой протокол, версия, ключи, sandbox, право нового PMS, подписки/аренда кассы/ФН/ОФД и цена подключения неизвестны. Требуется действующий договор продавца и поддерживаемая кассовая конфигурация; применимость 54-ФЗ и налоговые реквизиты проверяются отдельно.

## Направления обмена

| Сущность / операция | Подтверждённый предел и требование |
|---|---|
| Бронь / отмена брони | Не передаётся как сущность OTA; внутренний reference связывает расчёт с бронью |
| Доступность / цены проживания / ограничения | not_applicable; суммы строк чека не являются синхронизацией цен |
| Платёж / выплата | Источник Монета; кассовый статус не подтверждает движение денег |
| Фискальный документ | Предлагается Кей Календарь → согласованный провайдер через Монету, точный маршрут подтвердить |
| Статус / фискальные реквизиты / ссылка | Провайдер → Монета → PMS только по выданному контракту; отсутствие ссылки в RC не означает отсутствие чека |
| Возврат / коррекция | Возможность и автоматизация должны быть подтверждены по конкретной цепочке и схеме расчётов |

## Доставка, задержка и тестовая среда

Публичная инструкция RC не даёт полного транспортного контракта этого субпровайдера. Webhook/polling, подтверждение, таймауты и SLA неизвестны. Требуется тестовая касса/ОФД или согласованный безопасный план; тестовые чеки и реальные чеки строго разделяются. Не отправлять пробные фискальные документы в production без завершённой проверки схемы и разрешённой процедуры.

## Сопоставление, ошибки и восстановление (PROPOSED)

Связи: tenant → продавец/ИНН → договор Монеты → касса/ОФД → receipt_id → payment/refund/booking. Проверять собственника расчёта и агентские реквизиты; нельзя переиспользовать кассу другого tenant. Идемпотентный ключ отдельный для каждого фискального события/стадии расчёта. Timeout после отправки требует fetch статуса до повторного создания. Несогласованный повтор исправляется по процедуре поставщика, не вторым слепым чеком.

Применить [INT-CORE-005–008](../contract.md). Журнал: correlation ID, receipt ID, тип расчёта, masked seller ID, сумма/валюта, статус, код ошибки; без секретов и избыточных данных гостя. Ошибка фискализации создаёт очередь для ответственного и не меняет факт оплаты. После сбоя сверить реестр чеков, денег и возвратов, повторить только отсутствующие операции с исходным ключом. Для отсутствующей ссылки предусмотрено состояние «Чек сформирован, ссылка недоступна», только если подтверждены фискальные реквизиты.

## Конкретный следующий шаг и приёмка

1. Финансовый владелец согласует с Монетой и Первый ОФД совместимость договора Кей Календаря, клиента/налогового режима, версии кассы/ФФД и агентской модели. Получает schema и тарифы, фиксирует ответственность за возвраты/коррекции.
2. Архитектор выбирает один подтверждённый маршрут через Монету; отдельный native adapter разрабатывает только если того требует контракт. Это зависимость общего финансового потока, а не обещание 15 независимых интеграций.
3. Пройти тесты предоплаты, полного расчёта, частичного/полного возврата, неверного ИНН/налоговой ставки, повторного webhook, timeout, недоступного ОФД и восстановления. Сверить деньги и чек независимо; измерить задержку.
4. Gate: [LEG-007/008/009 и LG-07/08/09](../../research/legal/compliance.md), корректный tenant mapping, подтверждённая доставка и runbook. Непроверенная конфигурация отображается «Ожидает проверки», не «Подключено».

Связи: `INT-FIRSTOFD`, `INT-MONETA-BUSINESS`, `INT-CORE-005/006/008`; экраны финансов/платёжной настройки и детализации чека. Все технические правила и критерии выше являются предложением Кей Календаря; из RC подтверждены только перечень совместимых поставщиков и особенность в начале паспорта.
